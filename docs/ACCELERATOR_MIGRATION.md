# Accelerator and beamline migration

Updated 2026-11-10. Active implementation targets Minecraft 1.21.1, NeoForge 21.1.265, Java 21 and Nuclearcraft Neohaul 0.10.10. The old source remains reference material under `legacy-src/`; runtime classes use `block`, `block.entity`, `block.menu`, `client.screen`, `multiblock.accelerator`, `recipe`, `physics` and `compat.jei`.

## Runtime implementation

`QMDAccelerators` registers 71 individual parts: six controllers, structural and interface blocks, two ion sources, nine RF materials, nine magnet materials and 32 coolers. ZeroCore owns their controller attachment, merging, splitting, chunk suspension and save delegation. QMD validates the complete shell and beam path, whole RF/quadrupole/dipole assemblies, uniform materials, ring corner dipoles, source direction and the required input/output ports. Rings preserve their open central hole. Mass spectrometers validate seven-block-wide/seven-block-high alternating magnet/yoke and separation layers with four collectors above every source.

Linear accelerators consume real source items or source fluid, FE and particle amounts to produce a focused beam. Ring acceleration includes both the magnetic and radiation energy limit plus a synchrotron photon output. Decelerators lower energy using their operating percentage. Diverters and splitters route beams through their physical ports, apply bend losses and reject neutral magnetic bending; a straight diverter path permits neutral particles. Splitters retain the legacy floor division for odd particle counts. Exact long energies survive packets and persistence.

Mass spectrometers consume their real recipe inputs over the configured work duration, require power and cooling, and preserve all four item/fluid products with their chance, minimum and increment fields. Source and collector capabilities refer to their shared controller inventory/tanks rather than independent copies. Output collectors allow extraction, coolant/source inputs allow insertion, and simulation leaves state unchanged. Inventories drop when parts break.

Thermal behavior includes ambient heating, interior-volume storage scaling, exterior surface-area heat transfer, coolant temperature floors, fractional cooling work and optional quench explosions. All nine materials expose separate RF/magnet power, heat, efficiency and temperature configuration. Ion-source power/multiplier/focus and every cooler's rate and placement rule are configurable with validated rule syntax. Redstone ports switch between input and temperature output by crouch-right-clicking; their output is relative to the machine's maximum operating temperature. Controller operating percentage and port reversal are available through the actual menu.

`QMDBeamlines` registers the standalone three-axis beam conduit. Collinear loaded blocks share one bounded beam sample; extraction at either endpoint consumes it and applies whole-line attenuation once. Misaligned segments do not join. Capability lookups do not load chunks. Length/topology changes and sample expiry prevent stale particle replay. A lone conduit can change axis by crouch-right-clicking. The original model, collision width and textures are retained. Transient saved beam data is not emitted after load until a fresh beam arrives.

All controllers and ion sources have actual container menus and a full screen with player inventory, applicable machine slots, power/thermal bars, tanks, particle tooltips, validation errors, work progress and controls. Menu validity checks live block-entity identity, loaded position, owner and distance. State packets preserve exact long FE/particle energy and gate updates by container ID and position.

The computer port supplies `computerSnapshot()` and `computerSetPercentage(-1..100)` for server scripts, including KubeJS block-entity access. A snapshot contains controller statistics, beams and tanks; `-1` selects redstone. The old OpenComputers API has no dependency on this 1.21.1 target, so those specific optional callbacks are not linked. Their state/control functionality is exposed through these common methods.

## Recipes and JEI

The migrated catalog contains all 14 legacy ion-source recipes, all five cooling recipes and all 133 uncommented mass-spectrometer entries. Legacy metadata IDs are flattened, isotope tags use Neohaul's current `c:isotopes/<element>/<mass>` form, and optional material tags use conditional recipes. Crafting covers every accelerator part and beamline. Supporting recipes restore superconducting compounds/wires, seven alloy families, silicon boule/wafer production, N-doping irradiation, three processor tiers, iron fluoride and the Nd:YAG rod. Shared discharge-lamp/laser assembly prerequisites are documented by the main migration handoff.

JEI has source, cooling and spectrometer categories backed by the connected server's recipe manager. Categories show particle/fluid/item ingredients, thermal/work metadata and output chances. Catalysts include their machines and coolers. Screens expose the real tanks/beams under the cursor. Item transfer handles actual ion-source and spectrometer menus and excludes fluid tanks from inventory transfer.

## Verification and limits

The final integrated `./gradlew.bat build compileGameTestJava` passed in 23 seconds with all 80 JUnit tests passing and zero failures, errors or skips (`build/reports/migration/build-expanded-final-5.log`). `./gradlew.bat runGameTestServer` passed in 43 seconds with all 98 required tests passing; the game suite completed in 20.46 seconds (`build/reports/migration/gametest-expanded-final-2.log`). `./gradlew.bat runGameTestServer -PwithKubeJS` also passed in 48 seconds with all 99 required tests passing; the game suite completed in 23.03 seconds (`build/reports/migration/gametest-expanded-kubejs.log`).

Both GameTest runs include all eight accelerator tests (seven physical machine tests and one real server resource reload) and all three beamline tests. They verify linear output/source/FE consumption and disassembly, source persistence/menu identity, ring/synchrotron output, deceleration, charged/neutral diversion, splitting, the complete default 1000-work mass-spectrometer cycle with coolant automation, and beamline capability/attenuation/topology/expiry.

An earlier run exposed a configuration validator error accepting only singular `cooler` while ten shipped rules use `coolers`. Runtime matching already recognized those targets, but the config loader repeatedly rejected its own defaults. The parser now accepts both spellings, number words one through six, digits 1 through 6 and normalized whitespace/case. The final build passed both unit regressions covering all 32 shipped defaults and accepted/rejected grammar.

Headless tests cannot establish rendered GUI/model appearance or actual client packet delivery. Multiplayer delivery, client interaction, configured cooler-rule combinations, quench explosions and larger/cross-chunk geometry need further coverage; the existence of their implementation is not an in-game verification claim.

The final client parity audit found no legacy world-beam effect implementation: the legacy `AcceleratorRenderPacket` is empty and the accelerator/beamline classes contain no custom beam-rendering path. Their original block models/textures remain the visual representation. Accelerator glass now explicitly uses the translucent client layer, non-occluding geometry and hidden faces between adjacent glass blocks, restoring the legacy transparent-block behavior. No new world-beam effect was added as part of that audit. Glass rendering compiled with the integrated build; rendered inspection remains outstanding.
